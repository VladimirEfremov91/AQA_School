# Домашнее задание: сценарии и шаги Cucumber для сервиса бронирования столиков

Цель этого задания — научиться **правильно формулировать сценарии на Gherkin** и **корректно связывать их с определениями шагов**: подбирать формулировку, ключевые слова, тип параметра в Cucumber Expression, разносить логику по Background/Outline/тегам/хукам.

Бизнес-логику внутри Java-методов **реализовывать не нужно**. Метод шага может:

* просто вывести полученные параметры в консоль (`System.out.println`), или
* содержать заглушку `throw new io.cucumber.java.PendingException();`

Важно, чтобы у **каждого шага из `.feature`\-файла было ровно одно** (за исключением специально оговорённого случая в Блоке 8) подходящее определение с аннотацией и корректными параметрами — само тело метода не оценивается.

* * *

## Предметная область

Сервис бронирования столиков в ресторане «Vecher».

* В ресторане есть несколько столиков, у каждого — номер и вместимость (сколько гостей за него поместится).
* Клиент бронирует столик, указывая количество гостей и время.
* Бронь принимается, только если есть свободный столик с вместимостью не меньше числа гостей.
* Если подходящего столика нет — клиент получает отказ.
* Клиент может отменить своё бронирование.
* Иногда клиент оставляет особое пожелание свободным текстом (например: «столик у окна», «нужен детский стул»).

Как именно называть сценарии — решайте сами, главное, чтобы шаги были осмысленными и не противоречили друг другу.

* * *

## 🔵 Блок 1. Базовые сценарии

Создайте файл `booking.feature` и опишите три сценария обычными шагами `Given` / `When` / `Then` / `And` (без Background и без параметризации):

* успешное бронирование столика, когда вместимость достаточна;
* отказ в бронировании, когда все подходящие столики заняты или слишком маленькие;
* отмена ранее сделанного бронирования.

Требования к формулировкам:

* Пишите шаги на **естественном языке бизнеса** («гость забронировал столик на 4 человека»), а не техническим языком реализации («вызван метод bookTable с параметром 4»).
* Каждому шагу из `.feature` должен соответствовать ровно один Java-метод — для этого сразу заведите класс `BookingStep` и на каждый шаг напишите аннотацию с Cucumber Expression, дословно совпадающую с текстом шага.

## 🟢 Блок 2. Background

Посмотрите на сценарии из блока 1 — в каждом наверняка есть одинаковый исходный шаг (например, какие столики уже существуют в ресторане).

* Вынесите этот повторяющийся `Given`\-шаг в `Background`.
* Держите Background коротким (1–2 шага) — если хочется вынести больше, значит, часть логики на самом деле нужна не всем сценариям, и её стоит оставить внутри конкретного `Scenario`.
* можно сделать в отдельном файле или закомментировать первую реализацию без Предыстории.

## 🟡 Блок 3. Scenario Outline + Examples

Правило «бронь принимается, если вместимость столика ≥ числа гостей» удобно проверить не тремя разными сценариями, а одним шаблоном.

* Опишите `Scenario Outline`, который проверяет исход бронирования для **не менее четырёх** комбинаций «вместимость столика / число гостей».
* В таблице `Examples` должен быть как минимум один случай с успехом и один — с отказом.
* Названия столбцов должны сами объяснять, что в них лежит, без дополнительных комментариев.
* На эту таблицу тоже напишите step definitions с параметрами `{int}`/`{word}` — конкретный текст самих шагов выберите сами, лишь бы в них естественно читались значения из `<...>`. -Outline является дополнительным сценарием (можно оставить и старые, они не мешают)

## 🟣 Блок 4. Data Table

Добавлять столики по одному — долго. Опишите **один** шаг, который добавляет сразу несколько столиков одной таблицей, например:

```gherkin
Given в ресторане есть столики:
  | номер | вместимость |
  | 1     | 2           |
  | 2     | 4           |
  | 3     | 6           |
```

* Метод шага должен принимать `DataTable` последним параметром.
* Используйте `table.asMaps()` (или `asLists()`) внутри метода — реализовывать добавление в реальную коллекцию не обязательно, но структуру таблицы нужно корректно распарсить хотя бы в вывод в консоль.
* Примените этот шаг в одном из сценариев блока 1 или 3 вместо нескольких одиночных `Given`.

## 🟠 Блок 5. Doc String

Добавьте сценарий, где особое пожелание клиента передаётся большим текстом:

```gherkin
When гость оставляет пожелание к брони:
  """
  Пожалуйста, столик подальше от кухни,
  у вас там пахнет болотом.
  """
```

Метод должен принимать этот текст как `String` последним параметром.

## 🔴 Блок 6. Теги

Расставьте теги на сценариях из блоков 1–3:

* `@smoke` — на сценарий успешного бронирования;
* `@negative` — на все сценарии, где ожидается отказ;
* `@regression` — на весь `Feature` целиком (наследуется автоматически всеми сценариями внутри).

Продемонстрируйте (скриншотом консоли) два запуска:

1. только сценарии с `@smoke`;
2. все сценарии, кроме помеченных `@negative` (оператор `not`).

* * *

## 🟤 Блок 7. Hooks

Заведите отдельный класс `Hooks` с двумя простыми методами:

* `@Before` — печатает в консоль название сценария перед началом (используйте параметр `Scenario scenario`);
* `@After` — печатает в консоль, прошёл сценарий или упал (`scenario.isFailed()`).

Хук должен быть **один `@Before` и один `@After`**, без указания `order` и без привязки к тегам.

## ⭐ Блок 8\* (необязательно)

Во всём остальном задании шаги специально описываются только через Cucumber Expressions. Здесь — ровно наоборот: один шаг нужно осознанно описать классическим **регулярным выражением**, чтобы почувствовать, для чего оно нужно и чем отличается от Cucumber Expression.

Добавьте возможность изменить число гостей в уже существующей брони — в обе стороны:

```gherkin
When гость увеличивает бронь на 2 человека
When гость уменьшает бронь на 2 человека
```

* Не заводите два метода-близнеца. Опишите **один** метод, который ловит оба варианта через regex с группой-альтернативой.
