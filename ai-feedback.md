# AI-фидбек по архитектуре проекта (задание 18)

Этот файл — результат ревью кода проекта глазами ИИ-агента (OpenCode). Ревью сфокусировано на модуле `org.lesson17` (RestAssured-тесты), т.к. он расширялся в рамках домашнего задания 18. Анализ основан на фактическом состоянии файлов `ServeRestTest.java`, `CarrinhoTest.java` и `Usuario.java`.

## Что сделано хорошо

- **Использование Lombok для DTO.** `Usuario` использует `@Data` + `@NoArgsConstructor` + `@AllArgsConstructor` — лаконично и типобезопасно, правильный баланс между строками JSON и объектами.
- **Единая точка настройки теста** через `RestAssured.baseURI` в `@BeforeAll` — глобальная конфигурация не дублируется по тестам.
- **Изоляция нового покрытия.** `CarrinhoTest` вынесен в отдельный класс и самодостаточен (создаёт своего пользователя, товар и токен), поэтому не зависит от порядка/состояния `ServeRestTest`.
- **Хорошие `@DisplayName`** — читабельные сценарии на естественном языке.

## Наблюдения и риски

1. **`ServeRestTest` — негерметичный и порядок-зависимый.**
   Класс держит общее статическое состояние (`userEmail`, `userId`, `userToken`, `usuario`) и опирается на `@TestMethodOrder` + `@Order`. Если один тест падает, остальные «съезжают» каскадом. Это хрупко для CI.

2. **Жёсткая связанность с внешним сервисом.**
   Оба теста бьют в живой `https://serverest.dev`, у которого **БД сбрасывается каждый день**. Это и есть причина ранее падавшего `shouldGetAllProducts` (захардкоженное имя товара исчезало). Тесты требуют сети и непредсказуемы.

3. **Повторяющийся setup между классами** (`CarrinhoTest` создаёт юзера+товар, `ServeRestTest` — тоже). Хорошая точка для выноса в общий вспомогательный класс/утилиту или базовый класс тестов.

4. **Подсчёт глобальных списков.** `GET /carrinhos` возвращает корзины всех пользователей, поэтому ассерты вида `quantidade == 1` на весь список неверны — надо фильтровать по `idUsuario` (в тесте это уже учтено, но в `ServeRestTest` есть похожие «живые» допущения).

## Рекомендации

| Приоритет | Действие |
|---|---|
| Высокий | Сделать `ServeRestTest` герметичным: не хардкодить данные из БД, создавать и чистить за собой ресурсы (товары/корзины) в самом тесте. |
| Высокий | Добавить CI-флаг/материализацию сети или прогонять RestAssured-тесты отдельной задачей с явным допущением сети. |
| Средний | Вынести общий CRUD-сетап (регистрация юзера, логин, создание товара/корзины) в helper — убрать дублирование между классами. |
| Средний | Подумать над генерацией уникальных данных через `datafaker`/`System.currentTimeMillis()` (частично уже сделано) и согласовать конвенцию имён. |
| Низкий | Декомпозировать `ServeRestTest` на несколько классов по группам эндпоинтов (Login/Usuários/Produtos), как поступили с `CarrinhoTest`. |

## Итог

Архитектура для учебного проекта разумная: понятные DTO, читабельные сценарии, корректная сериализация. Главные точки роста — **герметичность** (устранить зависимость от сбрасываемой внешней БД и порядка тестов) и **устранение дублирования setup-логики** между тестовыми классами.
